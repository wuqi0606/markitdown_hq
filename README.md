# MarkItDown HQ — Dify 插件使用说明

基于微软 [MarkItDown](https://github.com/microsoft/markitdown) 0.1.8 的 Dify 文档处理插件，将 PDF、Word、Excel、PPT、HTML 等文档转换为干净的 Markdown，供知识库分段与向量化使用。

## 解决的核心问题

- **标题层级丢失** —— Word 文档的章节标题常用普通段落（「一、」「（一）」或自动编号）而非标题样式，转换后层级全丢，父子分段的分隔符失效。插件内置补齐（`restore_headings` 默认开启）。
- **列表序号错乱** —— 不同编号体系被合并重排成一条连续列表，正文写「详见（1）」而检索出的片段是「2. …」，交叉引用对不上号。插件按原始编号还原序号。
- **图片不可检索** —— 流程图、界面截图转出来只有二进制或链接，没有语义，检索永远命中不了。插件可用视觉模型为每张图生成中文描述。
- **PDF 页眉页脚混入正文** —— 每页的公司名、页码混进正文，向量化全是噪声。插件按入口分别清洗。

## 安装

插件 → 安装插件 → **通过 GitHub**：

1. 仓库填：`https://github.com/wuqi0606/markitdown_hq`
2. 版本选最新 tag，包文件选对应的 `markitdown_hq-<版本>.difypkg`
3. 安装

> 插件逻辑变更后，知识库里已入库的旧文档不会自动更新，需要重跑流水线重新入库。
> 升级顺序：先升级插件 → 再删旧文档 → 再重新上传。

## 在 Knowledge Pipeline 中的接法

### Word / Excel / PPT / HTML / Markdown / TXT 分支

```
FILE  →  MarkItDown HQ  →  Parent-child Chunker  →  Knowledge Base
```

走「文件」入口即可，插件会自动补齐标题层级。

> **md / txt 的标题层级会被重建**：md 可能整篇用 `##` 标章节，txt 可能连标记都没有，层级不整理父分隔符就匹配不到。插件按编号语义优先处理 —— 标题带编号的按编号重建，都不带编号的信任作者标的 `#` 级别，完全没有标记的按编号形态从正文推导。

> **不要用 Dify 内置的文档提取器处理 md**：它的 `MarkdownExtractor` 会删掉 `#` 标记，标题层级直接丢失。md 要走本插件。

### PDF 分支

MarkItDown 不抽取 PDF 内的图片，PDF 文档需先经 MinerU 解析（版面结构还原 + 抽图并上传），再把文本交给本插件：

```
FILE  →  MinerU  →  MarkItDown HQ (文本输入)  →  Parent-child Chunker  →  Knowledge Base
```

插件检测到文本输入时**跳过解析**，只做清洗、标题层级重建与图片处理。

> **PDF 分支的标题层级会按编号语义重建**。上游只输出二级标题且不区分层级，父分隔符匹配不到，父块会退化成按长度硬切。插件按编号体系分别处理：形态序（`一、` `（一）` `1、` `（1）`）按编号形态定层级；点分十进制（`1.1.1.`）按编号点数定层级；混合编号（`第X章` + `2.1`）的章与节同级做父块边界、章内小节做子块边界；上游漏标的「第X章」会被恢复。

> **PDF 分支的 HTML 表格会被转成 Markdown**，避免标签进向量、大表撑爆父块。

### 节点参数

| 参数                | 值            | 说明                           |
| ----------------- | ------------ | ---------------------------- |
| 文件                | 绑定数据源输出      | 与「上游解析文本」二选一，两者都填时以文件为准      |
| **上游解析文本**        | 绑定上游解析器的文本输出 | 填了则跳过解析（PDF 分支用）             |
| 清除转换噪声            | **是**        | 知识库场景务必开                     |
| **补齐标题层级**        | **是**        | **知识库场景必须开**，否则父子分隔符失效       |
| 清除 PDF 页眉页脚       | **是**        | PDF 源文件必开                    |
| 页眉页脚特征词           | 公司名等，逗号分隔    | **走「上游解析文本」入口时必填**           |
| **父块分隔符**         | 与分段节点一致      | 见下方「Parent-child Chunker 参数」 |
| **子块分隔符**         | 与分段节点一致      | 见下方「Parent-child Chunker 参数」 |
| **图片处理方式**        | 见下方说明        | 删除图片 / 上传并替换为链接 / 上传并生成描述    |
| **视觉模型（提供商/模型名）** | 见下方说明        | 仅「上传并生成描述」时必填                |
| 视觉模型提示词           | 默认值即可        | 可按文档类型定制                     |
| **输出调试信息**        | **入库时关闭**    | 注释块会被向量化成一个噪音分段，仅排查时打开       |


**图片处理方式怎么选**

| 档位       | 行为                         | 适用                    |
| -------- | -------------------------- | --------------------- |
| 删除图片     | 移除图片引用                     | 图片无价值的文档，如纯制度文件       |
| 上传并替换为链接 | 每张图上传 Dify 存储，替换为可访问链接     | 要保留原图                 |
| 上传并生成描述  | 上传之外，用视觉模型为每张图生成中文描述，插在链接前 | 操作指引、用户手册类，图片本身就是关键信息 |

描述是**并发**生成的（一次 6 张），几十张图的手册不会因为逐张等待模型而超时。

**视觉模型怎么填**

格式 `提供商ID/模型名`，例如火山引擎豆包：

```
langgenius/volcengine/volcengine/doubao-seed-2-0-pro-260215
```

- 提供商 ID 和模型名在 Dify「设置 → 模型供应商」页面可见
- 必须是**具备视觉能力**的模型
- 这是手填字符串而非模型选择下拉 —— Dify 的知识库流水线节点面板不支持模型选择组件
- 填写错误时，插件跳过描述并保留链接，不中断转换

**视觉模型提示词默认值**

```
用不超过120个字的中文概括这张图片的核心内容：图片类型（流程图/审批图/界面截图/架构图等）+ 关键节点、模块或字段。只输出描述本身，不要思考过程、不要解释、不要引号、不要分点。
```

## 排查

打开节点参数里的「输出调试信息」，输出开头会有一段注释：

```
<!-- conversion notices
[debug] received: image_mode='describe', model='...', restore_headings=True, clean_pdf=True, text_mode=False
[info] 文档名.docx: images uploaded 3, failed 0
[info] 文档名.docx: image descriptions generated 3, failed 0
-->
```

- `[debug] received` 行是插件**实际收到**的参数值，用于确认平台传参是否正确；
- `images uploaded N` / `image descriptions generated N` 用于确认图片链路；
- 单张图片描述失败会降级为仅保留链接，不影响其余图片。

## 已知限制

### 通用

- **旧版 `.doc`（Word 97-2003）不支持**，需先用 Word 另存为 `.docx`。
- **图片被清除后**，正文里「如下图所示」这类指代会失去配图。知识库场景通常用「上传并生成描述」。
- **目录页残留**按四种形态清理：`一、 xxx 3`、`[标题](#锚点)`、降级的 `标题名 3`、点线形态 `2.1.1. 登录......... 16`。若你的目录格式不在此列可能漏清，入库前确认已清理干净。
- 知识库流水线的插件节点面板不支持高级参数类型，插件参数只使用基础类型（文本/数字/布尔/下拉/文件）。

### PDF 直读（不接上游解析，直接把 PDF 传给插件）

这条路不要走。插件直读 PDF 用的是 MarkItDown 的 pdfminer 纯文本后端，三个缺陷叠加，结果对分段基本不可用：

- **不抽取图片** —— PDF 里的流程图、截图全部丢失，正文只剩文字。
- **表格被打散成断裂单元格** —— 例如 `| （内部使用 | 注意保密） |`。
- **不产出任何标题层级** —— 纯文本没有加粗标记，标题补齐判不出来。

PDF 一律走上文的 MinerU 分支。这三条在文本入口都不存在。

### MinerU 文本入口

- **页眉页脚不填特征词就完全不清洗**。这条入口按「整行命中关键词即删」判定，参数留空时整段跳过。文件入口则是「内置特征词 + 参数词」无条件清一轮。
- **点分十进制编号（`1.1.1.`）在章下没有三位编号子节时可能退化成 1:1** —— 检索返回的仍是父块，只是子块不再有独立语义。
- **超大的跨页表格仍可能是单个父块** —— 长度够但没有可识别的分组列时不拆分。这种表建议改用 docx 版。
