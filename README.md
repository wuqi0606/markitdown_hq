# MarkItDown HQ — Dify 插件使用说明

基于微软 [MarkItDown](https://github.com/microsoft/markitdown) 0.1.8 的 Dify 文档处理插件，

将 PDF、Word、Excel、PPT、HTML 等文档转换为干净的 Markdown，供知识库分段与向量化使用。

## 解决的核心问题

**标题层级丢失。** 不少 Word 文档的章节标题用的是**普通加粗段落**，
不是「标题1/2/3」样式。MarkItDown 靠样式映射生成 `#`，样式没标就全丢了——
转换后父子分段的 `\n#` / `\n##` 分隔符完全失效。

标题补齐已内置（`restore_headings` 参数，默认开启），三条规则：

1. **只补加粗的编号行**。`1. **预算制定**` 是加粗段落 → 真章节标题；
   `1. 发起申请` 是 Word 的自动编号列表项 → 属于列表内容，不提升。
   两者在转换后的 Markdown 里几乎一样，只有加粗能区分；误升会把列表项和真标题
   拉平，父子分段时整节内容会被并进同一个父块。
2. **层级按文档实际出现的编号形态动态映射**：文档同时出现「一、」和「1、」时，
   「一、」判 H1、「1、」判 H2；只有「1、」时判 H1。
   识别的编号形态：`第x章`、`一、`、`1、`、`附件x`、`（一）`、`（1）`。
   以分号/句号/逗号结尾的行视为正文不提升；冒号结尾的短行（如「评分标准：」）视为标题。
3. **补出的层级必须深于它前面最近的真实标题**，否则会出现「H1 套在 H2 里」的倒挂。

顺带清理：目录标题行（`目录` / `目 录` / `## 目录`）、标题里多余的 `**`
（`## **标题**`）、空标题行（单独一行 `#`）。

**图片不可检索。** 文档里的流程图、界面截图转出来只有二进制或链接，没有语义，
向量检索永远命中不了。本插件提供三档图片处理，最高档会用视觉模型为每张图生成
中文描述，让「开票流程是什么」这类问题能检索到流程图并返回原图。

## 与插件市场版 `yevanchen/markitdown` 的区别

|               | 市场版                    | 本插件                            |
| ------------- | ---------------------- | ------------------------------ |
| MarkItDown 版本 | 0.0.2a1                | **0.1.8**（当前稳定版）               |
| PDF 支持        | 依赖未声明，PDF 常失败          | `markitdown[docx,pdf]`，PDF 已实测 |
| 标题层级          | 不处理，丢失后无法分段            | **内置补齐**                       |
| PDF 页眉页脚      | 不处理，混入正文               | **内置清除**                       |
| 噪声清洗          | 无，输出原样返回               | base64 图片 / 空表格行 / 目录残留        |
| 图片处理          | 仅删除                    | **删除 / 上传链接 / 上传并生成描述**       |
| 上游文本接入        | 无                       | 可直接接收 MinerU 等解析器的输出             |
| 旧版 .doc 识别    | 报 `BadZipFile`，错误信息不可读 | 按文件头识别，输出明确指引                  |
| 多文件           | 拼接为分隔文本                | 逐份处理，失败项单独列出                   |

## 安装

插件 → 安装插件 → **通过 GitHub**：

1. 仓库填：`https://github.com/wuqi0606/markitdown_hq`
2. 版本选最新 tag（当前 `v0.0.18`），包文件选 `markitdown_hq-0.0.18.difypkg`
3. 安装

> 插件逻辑变更后，知识库里已入库的旧文档不会自动更新，需要重跑流水线重新入库。
> 升级顺序：先升级插件 → 再删旧文档 → 再重新上传。

## 在 Knowledge Pipeline 中的接法

### Word / Excel / PPT / HTML 分支

```
FILE  →  MarkItDown HQ  →  Parent-child Chunker  →  Knowledge Base
```

### PDF 分支

MarkItDown 的 pdfminer 后端**不抽取 PDF 内的图片**，PDF 文档建议先经 MinerU 解析
（版面结构还原 + 抽图并上传），再把文本交给本插件做清洗与图片描述：

```
FILE  →  MinerU  →  MarkItDown HQ (文本输入)  →  Parent-child Chunker  →  Knowledge Base
```

插件检测到文本输入时会**跳过解析**，只做清洗、标题补齐与图片处理。

### MarkItDown HQ 节点参数

| 参数 | 值 | 说明 |
|---|---|---|
| 文件 | 绑定数据源输出 | 与「上游解析文本」二选一，两者都填时以文件为准 |
| **上游解析文本** | 绑定上游解析器的文本输出 | 填了则跳过解析，只做清洗与图片处理（PDF 分支用） |
| 清除转换噪声 | **是** | 知识库场景务必开 |
| **补齐标题层级** | **是** | **知识库场景必须开**，否则父子分隔符失效 |
| **图片处理方式** | 见下方说明 | 删除图片 / 上传并替换为链接 / 上传并生成描述 |
| **视觉模型（提供商/模型名）** | 见下方说明 | 仅「上传并生成描述」时必填 |
| **视觉模型提示词** | 默认值即可 | 发送给视觉模型的提示词，可按文档类型定制 |
| **清除 PDF 页眉页脚** | **是** | PDF 源文件必开，清页眉页脚页码 |
| 页眉页脚特征词 | 公司名等，逗号分隔 | 额外补充的识别词。内置特征词（密级/编号/保密标识等）始终生效，填写后合并使用 |
| 添加元数据前置信息 | 否 | 引用显示的是文档名，一般不用 |
| **输出调试信息** | **入库时关闭** | 输出开头的转换注释块会被向量化成一个噪音分段，仅排查问题时打开 |

**图片处理方式怎么选**

| 档位 | 行为 | 适用 |
|---|---|---|
| 删除图片 | 移除图片引用 | 图片无价值的文档，如纯制度文件 |
| 上传并替换为链接 | 每张图上传 Dify 存储，替换为可访问链接 | 要保留原图 |
| 上传并生成描述 | 上传之外，用视觉模型为每张图生成中文描述，插在链接前 | 操作指引、用户手册类，图片本身就是关键信息 |

**视觉模型怎么填**

格式：`提供商ID/模型名`，例如火山引擎豆包：

```
langgenius/volcengine/volcengine/doubao-seed-2-0-pro-260215
```

- 提供商 ID 和模型名在 Dify「设置 → 模型供应商」页面可见
- 必须是**具备视觉能力**的模型（模型列表里带眼睛图标的）
- 注意：这是手填字符串而不是模型选择下拉——Dify 的知识库流水线节点面板目前不支持模型选择组件（会白屏），这是平台限制
- 填写错误（无斜杠 / 模型不存在）时，插件跳过描述并保留链接，不会中断转换

**视觉模型提示词默认值**

```
用不超过120个字的中文概括这张图片的核心内容：图片类型（流程图/审批图/界面截图/架构图等）+ 关键节点、模块或字段。只输出描述本身，不要思考过程、不要解释、不要引号、不要分点。
```

需要按文档类型调整时（比如要求描述表格列名、要求英文输出），直接改这个参数。

### Parent-child Chunker 参数

**父分段**

- Parent Mode：`Paragraph`
- Parent Delimiter：`\n# `
- Parent Max Length：`1200`

**子分段**

- Child Delimiter：`\n## `
- Child Max Length：`400`

> **分隔符末尾的半角空格不能删。** Dify 切父子块用的是 `text.split(分隔符)`，
> 分隔符被吃掉；而 `\n#` 正好是 `\n##` 的前缀 —— 父切分会先命中，把
> `## （一）项目注销` 啃成 `# （一）项目注销`，子分隔符在这块里再也匹配不上，
> 表现就是**每个父块只剩 1 个子块**。加上尾部空格后
> （`\n## ` 里 `#` 后面是 `#` 不是空格），两级分隔符各管各的。

> 原文档没有二级标题时，子分隔符不生效，会退化为按最大长度切分，
> 不影响使用，只是子段语义边界弱一些。

## 排查

打开节点参数里的「输出调试信息」，输出开头会有一段注释：

```
<!-- conversion notices
[debug] received: image_mode='describe', model='...', restore_headings=True, clean_pdf=True, text_mode=False
[info] 文档名.docx: images uploaded 3, failed 0
[info] 文档名.docx: image descriptions generated 3, failed 0
-->
```

- `[debug] received` 行是插件**实际收到**的参数值，用于确认平台传参是否正确；
- `images uploaded N` / `image descriptions generated N` 用于确认图片链路；
- 单张图片描述失败会降级为仅保留链接并写入提示，不影响其余图片。

排查完记得把「输出调试信息」关掉再入库。

## 已知限制

- **旧版 `.doc`（Word 97-2003）不支持**。即使后缀是 `.docx`，若文件头是 `D0 CF 11 E0`
  则无法解析，需先用 Word 另存为真正的 `.docx`。插件会在输出开头的
  `<!-- conversion notices -->` 注释里明确列出。
- **PDF 内的图片不会被 MarkItDown 抽取**。PDF 文档请走 MinerU 分支，
  由 MinerU 抽图后以文本形式交给本插件。
- 图片被清除后，正文里「如下图所示」这类指代会失去配图。如需保留图片，
  将「图片处理方式」设为「上传并替换为链接」。知识库场景下过大的图片数据会损害向量化质量，
  通常用「上传并生成描述」——描述进向量，原图按链接返回。
- 目录页残留按四种形态清理：`一、 xxx 3`、`[标题](#锚点)`、降级的 `标题名 3`、
  以及 PDF/MinerU 目录页的点线形态 `2.1.1. 登录......... 16`（含多条目粘连成一行的情况）。
  若你的文档目录格式仍不在此列，可能漏清，检查方式：转换后搜索输出里是否还有带页码的章节标题。
  **目录残留会形成大量垃圾分段，且很容易在向量检索中压过正文分段，建议入库前确认已清理干净。**
- **PDF 页眉页脚按「重复即页眉」启发式判定**：短行重复出现 ≥2 次且含特征词才删。
  特征词 = 你在「页眉页脚特征词」参数里填的词（如公司名）+ 内置通用词
  （密级标识、文件编号、保密标识等）。页码按「距最近已删页眉 ≤3 行」判定。
  如果只靠内置特征词删不干净，把公司名填进参数即可。
- **PDF 表格会被打散成断裂单元格**，例如
  `| （内部使用 | 注意保密） |     |`。这是 PDF 无表格结构的固有问题，
  本插件无法还原。若某份 PDF 的表格内容重要，建议改用 docx 版、人工校对，
  或走 MinerU 分支（其表格结构识别效果更好，会直接转成 HTML 表格）。
- 知识库流水线的插件节点面板不支持高级参数类型（如模型选择器），
  插件参数只使用基础类型（文本/数字/布尔/下拉/文件）。
