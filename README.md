# MarkItDown HQ — Dify 插件使用说明

基于微软 [MarkItDown](https://github.com/microsoft/markitdown) 0.1.8 的 Dify 文档处理插件，

将 PDF、Word、Excel、PPT、HTML 等文档转换为干净的 Markdown，供知识库分段与向量化使用。

## 解决的核心问题

**标题层级丢失。** 不少 Word 文档的章节标题用的是**普通段落**（手打编号
「一、」「（一）」，或 Word 自动编号），不是「标题1/2/3」样式。
MarkItDown 靠样式映射生成 `#`，样式没标就全丢了——
转换后父子分段的 `\n# ` / `\n## ` 分隔符完全失效。

标题补齐已内置（`restore_headings` 参数，默认开启）。

**Word 走直读 OOXML 的路子**，不看转换后的纯文本。原因：转换那一步已经把
最关键的信息丢掉了 ——

| 被丢掉的信息 | 后果 | 插件怎么补回来 |
| --- | --- | --- |
| 段落的大纲级别（`w:outlineLvl`） | 作者标了「这是 2 级标题」，但样式名不是 `heading 2`，mammoth 不认 | 段级/样式级 `outlineLvl` 直读，**实测有 278 个标题被完全漏掉** |
| 字号与字体 | 标题用黑体/楷体 16 磅，正文用仿宋 16 磅 —— 同字号，只能靠字体区分 | 按 **run 级 → 样式级 → 文档默认级** 三级回落取字体/字号 |
| 自动编号体系（`numId` / `lvlText`） | 「一、编制目的」变成「编制目的」，编号整个丢了 | 从 `numbering.xml` 还原原始编号，标题文本与目录一致 |

判定分三路（信号强度递减）：

1. **真实标题** —— mammoth 已经渲染成 `#` 的段落。层级直接用 `#` 的个数
   （与 Word 样式表里的 `outlineLvl` 实测完全一致）。额外把它的编号形态
   登记进「章节链」。
2. **强真标题** —— 作者设了大纲级别、但 mammoth 没转成 `#` 的段落。
   用**字体/字号复核**过一道：作者常把正文也设成大纲级别
   （「1、负责仓库管理制度的编制和优化」就是大纲级别 2 的正文），
   标题用黑体/楷体，正文用仿宋/宋体，靠这个分开。
3. **伪标题** —— 靠字号/字体/加粗，以及「同一编号组内全是短标题 → 整组是标题」
   的组投票推断出来的。

层级不靠全局猜形态序，而是维护一条**章节链**（形态 → 层级的当前映射）：
遇到形态 F 就关闭比 F 更细的形态；F 已在链上 → 同一层级（兄弟）；
否则比链上更粗的最深章节深一层。形态序：
`第x章/第x部分` < `一、` < `第x条` < `（一）` < `1、` < `（1）`。

这样「（一）项目注销」下面的「1. 发起申请」自动是 H3，同一章里的第二个
「1. xxx」还是 H3 —— 不需要全局猜形态序，也不会出现「H1 套在 H2 里」的倒挂。

**目录区块与封面区整体跳过**（`目 录` 到下一个标题之间的条目、
以及封面上的公司名/文件名/版本管理记录）—— 它们常被作者设成大纲级别 1，
补进去会把文档骨架搞乱。

顺带清理：目录标题行（`目录` / `目 录` / `## 目录`）、标题里多余的 `**`
（`## **标题**`）、空标题行（单独一行 `#`）。

**畸形嵌套列表。** Word 的自动编号列表如果某一层是「孤立」的（该编号体系下
没有更浅的层级可挂靠），mammoth 会给它补一个虚拟父级 `<ul>`，把真正的有序
列表套进去 —— markdownify 忠实翻译成：

```
* 1. 费用已结清的，即项目所有物资完成返库，…
  2. 费用未结清的，即合同不合作，…
```

多出来的 `* ` 是虚拟父级的残留。而且按 CommonMark 解析，续行缩进不足 3 空格
会被当成上一项的**惰性续行**，整组列表塌成一段文字。插件会去掉这个多余的
`* ` 并把续行缩进回收，让它回到正常的 `1.` / `2.` 有序列表。

修复只认一种形态（行首 `* N.` + 后续缩进的 `N.`，且续行序号连续递增），
真正的 bullet 列表每行都带 `*`，不会被误伤；再叠加 XML 交叉验证 ——
只有确认该段落确实是「自动编号的有序列表」才动手。

**列表序号错乱。** mammoth 把**不同编号体系**的列表**合并重排**成一条连续的
有序列表。源文档里明明是四套独立编号（`1.` / `（1）` / `(1)` …），全被渲染成
`1.` `2.` `3.` `4.` —— 序号和形态全错。后果是**交叉引用对不上号**：正文写
「详见（1）」，检索出的片段却是「2. 提前实施…」，模型按编号引用会引错条款。

插件从 `numbering.xml` 的 `lvlText` 模板 + 每段落的计数快照还原真实序号。
**只还原序号、不还原形态** —— 形态还原成 `（1）` 会让列表项不再是 markdown
列表（CommonMark 下缩进续行会合并成一个 paragraph，整组列表塌成文字），
序号还原成 `1.` 才能保住 `list_item` 结构。

> PDF / 图片 / 文本输入拿不到 XML，走纯文本规则：整行加粗 + 编号形态 + 不是句读结尾。

**图片不可检索。** 文档里的流程图、界面截图转出来只有二进制或链接，没有语义，
向量检索永远命中不了。本插件提供三档图片处理，最高档会用视觉模型为每张图生成
中文描述，让「开票流程是什么」这类问题能检索到流程图并返回原图。

## 与插件市场版 `yevanchen/markitdown` 的区别

|               | 市场版                    | 本插件                            |
| ------------- | ---------------------- | ------------------------------ |
| MarkItDown 版本 | 0.0.2a1                | **0.1.8**（当前稳定版）               |
| PDF 支持        | 依赖未声明，PDF 常失败          | `markitdown[docx,pdf]`，PDF 已实测 |
| Excel 支持      | 依赖未声明，xlsx 常失败        | `markitdown[docx,pdf,xlsx]`，xlsx 已实测 |
| 标题层级          | 不处理，丢失后无法分段            | **内置补齐**                       |
| PDF 页眉页脚      | 不处理，混入正文               | **内置清除**                       |
| 噪声清洗          | 无，输出原样返回               | base64 图片 / 空表格行 / 目录残留        |
| 图片处理          | 仅删除                    | **删除 / 上传链接 / 上传并生成描述**       |
| 上游文本接入        | 无                       | 可直接接收 MinerU 等解析器的输出             |
| 旧版 .doc 识别    | 报 `BadZipFile`，错误信息不可读 | 按文件头识别，输出明确指引                  |
| 多文件           | 拼接为分隔文本                | 逐份处理，失败项单独列出                   |
| 全部失败          | 返回空字符串，无从判断         | 输出明确失败原因（文件名 + 异常）             |

## 安装

插件 → 安装插件 → **通过 GitHub**：

1. 仓库填：`https://github.com/wuqi0606/markitdown_hq`
2. 版本选最新 tag（当前 `v0.0.33`），包文件选 `markitdown_hq-0.0.33.difypkg`
3. 安装

> 插件逻辑变更后，知识库里已入库的旧文档不会自动更新，需要重跑流水线重新入库。
> 升级顺序：先升级插件 → 再删旧文档 → 再重新上传。

> **依赖是安装时装的，升级插件版本才会装上**。xlsx 转换需要 `pandas` + `openpyxl`
> （`markitdown[xlsx]` extra），缺了会静默产出空内容；v0.0.30 起失败时会直接
> 报出原因，不会再返回空字符串。

## 在 Knowledge Pipeline 中的接法

### Word / Excel / PPT / HTML 分支

```
FILE  →  MarkItDown HQ  →  Parent-child Chunker  →  Knowledge Base
```

### Markdown / TXT 分支

```
FILE  →  MarkItDown HQ  →  Parent-child Chunker  →  Knowledge Base
```

走「文件」入口即可，插件会自动补齐标题层级重建。

> **md / txt 的标题层级会被重建**：这两类格式没有 docx 的 XML 结构，也没有 PDF 上游的章节标记 —— md 可能整篇都用 `##` 标章节，txt 则可能连标记都没有。层级不整理，父分隔符 `\n# ` 一个都匹配不到，父块会退化成「按长度硬切」。插件按**编号语义优先**处理：标题文本里带编号的（`2.1.1` / `一、` `（一）`）按编号重建层级；标题都不带编号的（人手写的 md）信任作者标的 `#` 级别；完全没有标记的（txt）按编号形态从正文推导。md 里的代码围栏会被保护，`# 注释` 与 `1. xxx` 这类行不会被误当标题。Word / PDF 分支不受影响。

> **不要用 Dify 内置的文档提取器处理 md**：它的 `MarkdownExtractor` 会把 `#` 标记删掉（`re.sub(r"#", "", key)`），标题层级直接丢失。md 要走本插件。

### PDF 分支

MarkItDown 的 pdfminer 后端**不抽取 PDF 内的图片**，PDF 文档建议先经 MinerU 解析
（版面结构还原 + 抽图并上传），再把文本交给本插件做清洗与图片描述：

```
FILE  →  MinerU  →  MarkItDown HQ (文本输入)  →  Parent-child Chunker  →  Knowledge Base
```

插件检测到文本输入时会**跳过解析**，只做清洗、标题补齐、标题层级归一化与图片处理。

> **PDF 分支的标题层级会被归一化**：MinerU 把章节标成 `##`（二级），而 Dify 父子分段的父分隔符 `\n# ` 只认一级标题 —— 差一层，父块就会退化成「按长度硬切」，检索时整篇文档被丢给模型。插件会把 ≥2 级标题上移一级（让章节落到一级标题），并把「后面紧跟下一个标题」的空壳标题降一级。Word 分支不受影响。

> **PDF 分支的标题从属关系会按编号形态重排**：上游有时会把普通条目误判成章节（实测销售开票办法的 `## 7、开票时限：` 其实是「四、销售开票」章下的第 7 条），它会变成独立父块、把真正的章从中间切断；章下的条目也切不成子段，父子结构退化成 1:1。插件按编号形态重建层级：形态序体系（`一、` `（一）` `1、` `（1）`）下章=一级标题、条=二级标题、款降回正文。Word 分支不受影响。

> **点分十进制编号的 PDF（`1.1.1.`）按编号点数重建层级**：上游会把点分体系的**所有**章节都标成二级标题，不区分点数；若再叠加「空壳标题降级」，层级就只取决于「标题后面有没有正文」——章节标题和它自己的内容会被拆到两个父块，检索「2.2. 首页」会返回上一节「退出」的正文。插件改为按点数重建：两位编号=一级标题（父块边界）、三位编号=二级标题（子块边界）、顶层编号（`1.` `2.`）自己开启父块、四位以上降回正文；章节内的小标题（如「操作步骤」）也降回正文。两种编号写法都认（`2.2.1. 我的主页` 和 `2.9.1.应签台账`）。顶层章节若是空壳（后面直接跟第一节），会与那一节合并成同一个父块，避免出现只有标题的空壳父块。

> **序号连续性判定把上游误判成标题的条目也算进去**：形态序里 `1、` `2、` 只有在同一作用域内序号连续时才提升为标题（防误伤），但上游标成标题的行也带着自己的序号，必须一起参与判定 —— 否则序列里会出现空洞（`1,2,3,4,5,6,__,8`），后面的条目被判为孤立条目、不提升为标题，会粘在前一条的正文里（实测「四、销售开票」下的 `8、财务管理中心需每月输出开票报告…` 曾和 `7、开票时限：` 落进同一个子分段）。

> **混合编号体系的 PDF（章用「第X章」、节用点分）也能正确分段**：用户手册常这么写 —— `第一章 引言` / `1.1. 编写目的` / `第二章 首页` / `2.1 项目经理工作台`（实测项目交付操作指引 41 页 6 章全是这种结构）。此时整篇会被判定为点分体系，而「第X章」不是点分编号 —— 修复前它被当成「章内普通小标题」降成正文，`#` 标记消失 → 父分隔符 `\n# ` 匹配不到 → 整章被并进上一章的父块，检索「第二章 首页」返回的是第一章的正文。修复后：`第X章` 与顶层点分编号同为一级标题（父块边界），章内点分编号为二级标题（子块边界），章内子节同为二级标题。

> **上游漏标的章标题会被恢复**：MinerU 偶尔漏标章标题（实测「第三章 个人中心模块」落在 PDF 第 15 页底部、紧邻页脚，没被标成标题）→ 它被当成正文 → 整章并进上一章的父块。插件会把它恢复成一级标题。判据很严：文档里已有别的「第X章」标题（证明本文档确实用这套编号）、章号与已标记章号相邻（是序列里缺的那个）、整行是短标题形态（不含句读与「了/的/着」等虚词）、且后面紧跟的点分标题首段数字与章号一致（「第三章」后面跟着「3.1」）。正文里提到「第三章」的句子、目录残留、表格行都不会被误判。

> **章内小节不会被降成正文**：Dify 父子分段只有 `\n# ` / `\n## ` 两级分隔符，小节没有第三级可用。但把小节降成正文会让**标题与它的正文落进不同的子块** —— 实测「3.1.1 正常立项」成了上一子块的末行，正文却成了下一子块的首行，检索命中后模型看到的是标题、没有内容。章内小节现在与章内节同级（都是二级标题），至少保证二者同块。

> **PDF 分支的 HTML 表格会被转成 Markdown**：MinerU 把表格输出成 HTML，`<td>` / `rowspan` 这些标签会进向量当噪音，而且表格内部切不出边界，Dify 的长度兜底只能硬切（实测切出 3984 字的半截表格）。插件会把 HTML 表格转回标准 Markdown 并展开合并单元格；表够大且有清晰分组列时，还会按组拆开（每组前插一个标题，归一化后成为独立父块）。实测用户手册最大父块 3984 字 → 1792 字，HTML 标签清零。Word 分支的表格本来就是 Markdown，不受影响。

### MarkItDown HQ 节点参数

| 参数 | 值 | 说明 |
|---|---|---|
| 文件 | 绑定数据源输出 | 与「上游解析文本」二选一，两者都填时以文件为准 |
| **上游解析文本** | 绑定上游解析器的文本输出 | 填了则跳过解析，只做清洗、标题层级归一化与按形态重排、HTML 表格转换与图片处理（PDF 分支用） |
| 清除转换噪声 | **是** | 知识库场景务必开 |
| **补齐标题层级** | **是** | **知识库场景必须开**，否则父子分隔符失效 |
| **图片处理方式** | 见下方说明 | 删除图片 / 上传并替换为链接 / 上传并生成描述 |
| **视觉模型（提供商/模型名）** | 见下方说明 | 仅「上传并生成描述」时必填 |
| **视觉模型提示词** | 默认值即可 | 发送给视觉模型的提示词，可按文档类型定制 |
| **清除 PDF 页眉页脚** | **是** | PDF 源文件必开，清页眉页脚页码 |
| 页眉页脚特征词 | 公司名等，逗号分隔 | 额外补充的识别词。内置特征词（密级/编号/保密标识等）始终生效，填写后合并使用 |
| **输出调试信息** | **入库时关闭** | 输出开头的转换注释块会被向量化成一个噪音分段，仅排查问题时打开 |

**图片处理方式怎么选**

| 档位 | 行为 | 适用 |
|---|---|---|
| 删除图片 | 移除图片引用 | 图片无价值的文档，如纯制度文件 |
| 上传并替换为链接 | 每张图上传 Dify 存储，替换为可访问链接 | 要保留原图 |
| 上传并生成描述 | 上传之外，用视觉模型为每张图生成中文描述，插在链接前 | 操作指引、用户手册类，图片本身就是关键信息 |

**视觉模型怎么填**

格式：`提供商ID/模型名`，例如火山引擎豆包：

```
langgenius/volcengine/volcengine/doubao-seed-2-0-pro-260215
```

- 提供商 ID 和模型名在 Dify「设置 → 模型供应商」页面可见
- 必须是**具备视觉能力**的模型（模型列表里带眼睛图标的）
- 注意：这是手填字符串而不是模型选择下拉——Dify 的知识库流水线节点面板目前不支持模型选择组件（会白屏），这是平台限制
- 填写错误（无斜杠 / 模型不存在）时，插件跳过描述并保留链接，不会中断转换

**视觉模型提示词默认值**

```
用不超过120个字的中文概括这张图片的核心内容：图片类型（流程图/审批图/界面截图/架构图等）+ 关键节点、模块或字段。只输出描述本身，不要思考过程、不要解释、不要引号、不要分点。
```

需要按文档类型调整时（比如要求描述表格列名、要求英文输出），直接改这个参数。

### Parent-child Chunker 参数

**父分段**

- Parent Mode：`Paragraph`
- Parent Delimiter：`\n# `
- Parent Max Length：`1200`

**子分段**

- Child Delimiter：`\n## `
- Child Max Length：`400`

> **分隔符末尾的半角空格不能删。** Dify 切父子块用的是 `text.split(分隔符)`，
> 分隔符被吃掉；而 `\n#` 正好是 `\n##` 的前缀 —— 父切分会先命中，把
> `## （一）项目注销` 啃成 `# （一）项目注销`，子分隔符在这块里再也匹配不上，
> 表现就是**每个父块只剩 1 个子块**。加上尾部空格后
> （`\n## ` 里 `#` 后面是 `#` 不是空格），两级分隔符各管各的。

> 原文档没有二级标题时，子分隔符不生效，会退化为按最大长度切分，
> 不影响使用，只是子段语义边界弱一些。

## 排查

打开节点参数里的「输出调试信息」，输出开头会有一段注释：

```
<!-- conversion notices
[debug] received: image_mode='describe', model='...', restore_headings=True, clean_pdf=True, text_mode=False
[info] 文档名.docx: images uploaded 3, failed 0
[info] 文档名.docx: image descriptions generated 3, failed 0
-->
```

- `[debug] received` 行是插件**实际收到**的参数值，用于确认平台传参是否正确；
- `images uploaded N` / `image descriptions generated N` 用于确认图片链路；
- 单张图片描述失败会降级为仅保留链接并写入提示，不影响其余图片。

排查完记得把「输出调试信息」关掉再入库。

## 已知限制

- **旧版 `.doc`（Word 97-2003）不支持**。即使后缀是 `.docx`，若文件头是 `D0 CF 11 E0`
  则无法解析，需先用 Word 另存为真正的 `.docx`。插件会在输出开头的
  `<!-- conversion notices -->` 注释里明确列出。
- **PDF 内的图片不会被 MarkItDown 抽取**。PDF 文档请走 MinerU 分支，
  由 MinerU 抽图后以文本形式交给本插件。
- 图片被清除后，正文里「如下图所示」这类指代会失去配图。如需保留图片，
  将「图片处理方式」设为「上传并替换为链接」。知识库场景下过大的图片数据会损害向量化质量，
  通常用「上传并生成描述」——描述进向量，原图按链接返回。
- 目录页残留按四种形态清理：`一、 xxx 3`、`[标题](#锚点)`、降级的 `标题名 3`、
  以及 PDF/MinerU 目录页的点线形态 `2.1.1. 登录......... 16`（含多条目粘连成一行的情况）。
  若你的文档目录格式仍不在此列，可能漏清，检查方式：转换后搜索输出里是否还有带页码的章节标题。
  **目录残留会形成大量垃圾分段，且很容易在向量检索中压过正文分段，建议入库前确认已清理干净。**
- **PDF 页眉页脚按两条不同规则判定**（取决于走哪条入口）：
  - **文件入口**（直接把 PDF 传给插件）：按「重复即页眉」启发式 —— 短行重复出现
    ≥2 次且含特征词才删。特征词 = 你在「页眉页脚特征词」参数里填的词（如公司名）
    + 内置通用词（密级标识、文件编号、保密标识等）。页码按「距最近已删页眉 ≤3 行」判定。
  - **上游解析文本入口**（PDF → MinerU → 插件文本框）：MinerU 已经清掉了大部分页眉，
    残留的往往**只出现 1 次**，「重复」启发式抓不到。所以这条入口改成
    **「你填了关键词 → 整行命中即删」**：整行去掉关键词后只剩标点或少量修饰语
    （如 `编制：中科美络科技股份有限公司`）才判为页眉，正文句子
    （`本手册由中科美络科技股份有限公司编制`）不会误伤。相邻的孤立数字行
    （页码）一并删除。
  - 两种入口都要开「清除 PDF 页眉页脚」；只靠内置特征词删不干净时，把公司名填进参数。
- **PDF 表格会被打散成断裂单元格**，例如
  `| （内部使用 | 注意保密） |     |`。这是 PDF 无表格结构的固有问题，
  本插件无法还原。若某份 PDF 的表格内容重要，建议改用 docx 版、人工校对，
  或走 MinerU 分支（其表格结构识别效果更好，会直接转成 HTML 表格，
  本插件会把它转回标准 Markdown 并展开合并单元格）。
- 知识库流水线的插件节点面板不支持高级参数类型（如模型选择器），
  插件参数只使用基础类型（文本/数字/布尔/下拉/文件）。
- **点分十进制编号的 PDF（`1.1.1.`）仍可能是 1:1**：层级由编号点数决定，
  章下面没有三位编号的子节时子分隔符 `\n## ` 无事可切，父子结构退化。
  检索返回的仍是父块（内容正确），只是「子块」不再有独立语义。
  形态序编号（`一、` `（一）` `1、`）的文档不受此限 —— 会按形态重排出两级结构。
- **超大的跨页表格仍可能是单个父块**。表格会转成 Markdown，但如果它没有
  可识别的分组列（例如每行都是一个独立记录），就不会拆分 —— 父块会一直保持
  整张表的篇幅。这种表建议改用 docx 版或人工校对。
